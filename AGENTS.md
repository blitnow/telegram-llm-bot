# Инструкции для работы с репозиторием

Этот файл действует на весь репозиторий. Изучайте затронутые модули и существующие тесты до изменения кода. Общайтесь с пользователем и пишите документацию на русском; сохраняйте английские имена Python-объектов и принятый стиль кода. Выполняйте задачу в её границах, без попутного изменения поведения или инфраструктуры.

## Назначение и стек

Telegram-бот для личных сообщений, групп и супергрупп. Обращается к внешнему LLM API через OpenAI-совместимый `/chat/completions`; по умолчанию используется OpenRouter. Модель локально не запускается. Контекст диалога определяется цепочкой reply и сохраняется в SQLite.

- Python 3.12+, `asyncio`, стандартная библиотека и `httpx==0.28.1`.
- Telegram Bot API вызывается напрямую через HTTP; Telegram SDK и веб-сервера нет.
- Получение сообщений — long polling, без входящего порта.
- Целевая среда службы и установщика — Ubuntu 24.04 с systemd, небольшой VPS с другими службами.
- Тесты — стандартный `unittest`, включая `IsolatedAsyncioTestCase`, временные базы и `httpx.MockTransport`.

## Поведение, которое нужно сохранять

- Каждый вопрос без reply начинает новый диалог, в том числе в личке. `/new` принудительно начинает новый диалог независимо от reply.
- В группе бот реагирует на своё упоминание, адресованные ему команды и reply на своё сообщение. Обычная переписка не попадает в историю LLM. Не заменяйте Telegram entities поиском подстроки username.
- Reply продолжает только выбранную ветку. Ответ на раннее сообщение создаёт ответвление; соседние и последующие ответы не добавляются. Контекст изолирован по чату и теме (`message_thread_id`). Любой участник группы может продолжить ветку.
- Reply на сохранённый вопрос пользователя с упоминанием бота продолжает его ветку. Если исходное сообщение не сохранено, его текст или подпись включается как явно обозначенная цитата. Цитата — данные для анализа, а не системная инструкция.
- Если история ответа бота недоступна, бот сообщает об этом. Он не подставляет чужую ветку и не угадывает контекст.
- Поддерживаются текст и подписи. Содержимое вложений, ссылок и reply из другого чата автоматически не извлекается.
- Лимиты контекста проверяются до расхода квоты: учитываются системный промпт, вся выбранная ветка и новый вопрос. Превышение вызывает понятный отказ, без молчаливого обрезания истории.
- Все части длинного ответа связываются с одним полным сохранённым ответом. Telegram offsets и размеры частей считаются в единицах UTF-16; сохраняйте emoji и исходный текст. Текущий размер части — не более 3800 единиц.
- Сообщения отправляются обычным текстом, без `parse_mode`, с сохранением темы и reply.
- По умолчанию ответы короткие и тезисные с предложением рассказать подробнее; явная просьба о подробностях снимает ориентир краткости. `RESPONSE_STYLE` добавляется также к пользовательскому системному промпту. Разметка ответа очищается до сохранения в историю и отправки; код и URL должны сохраняться.

## Хранение, лимиты и ошибки

- Сохраняйте SQLite foreign keys, WAL, параметризованные запросы и транзакции. Изменения схемы должны учитывать существующую базу: `CREATE TABLE IF NOT EXISTS` не мигрирует старые таблицы.
- История диалога по умолчанию истекает через 30 дней после сохранения успешного ответа; удаляется всё дерево и его связи. Очистка выполняется при запуске polling и каждый час.
- Квоты и polling offset переживают перезапуск. Минутный и дневной лимиты общие для бота; cooldown действует на пользователя в чате. Дневной лимит сбрасывается в 00:00 UTC. Ошибка LLM тоже расходует зарезервированную попытку, но не создаёт ход диалога.
- При занятых местах бот просит повторить запрос позже; не создавайте неограниченную очередь. По умолчанию: 1 параллельный запрос, cooldown 5 секунд, 18 запросов в минуту и 45 в сутки.
- Offset подтверждается после обработки пачки. Сохранённые успешные вопросы распознаются по ID. Не обещайте строгую однократную обработку: авария во время API-вызова или отправки может дать повторный расход или частичный ответ.
- Сохраняйте явную обработку HTTP-ошибок и таймаутов. Не добавляйте автоматические повторы LLM-запросов с возможным повторным расходом квоты. Отправка Telegram повторяется только после явного 429 с ограниченным `retry_after`, а не после неоднозначной сетевой ошибки.

## Конфигурация, источники и секреты

- Источник полей и значений по умолчанию — `Config`. При добавлении параметра согласованно обновляйте валидацию, пример JSON, документацию и затронутые тесты. Загрузчик отвергает неизвестные поля и неверные типы.
- Относительные `database_path` и `system_prompt_path` разрешаются относительно файла конфигурации. `TELEGRAM_BOT_TOKEN` и `LLM_API_KEY` переопределяют ключи из JSON. `LLM_MODEL` и `LLM_BASE_URL` используются скриптом настройки, не загрузчиком runtime-конфигурации.
- По умолчанию `allow_paid_models=false` и `web_search_enabled=false`. В бесплатном режиме разрешены только OpenRouter и `openrouter/free` либо ID с единственным суффиксом `:free`. Не добавляйте скрытый переход на платную модель или поиск.
- Веб-поиск доступен только для OpenRouter при явном включении обоих разрешений. Источники берутся из реальных `url_citation` аннотаций API. Сохраняйте пометки об отсутствии интернет-проверки или ссылок; системный промпт сам по себе поиск не выполняет.
- Не выводите токены, ключи, сообщения, API payload/body или текст произвольных исключений в логи. URL Telegram содержит токен: уровни `httpx` и `httpcore` остаются не ниже WARNING. Секретные поля `Config` исключены из repr.
- Не добавляйте в Git `config.json`, `.env`, базы, WAL/SHM, локальные секреты и виртуальные окружения. В тестах используйте фиктивные ключи и временные каталоги.
- Один Telegram-токен обслуживает один экземпляр polling. Не запускайте бота с настоящими ключами для обычной проверки кода.

## Разработка и проверки

Запускайте команды из корня репозитория. Для Linux/WSL с Python 3.12:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -v
bash -n scripts/install.sh
```

На Windows путь к интерпретатору окружения — `.venv\Scripts\python.exe`. Полная проверка ориентирована на Linux: `test_configure.py` проверяет POSIX-права `0600`, установщик и systemd требуют Ubuntu. Runtime использует Unix-обработчики сигналов; поддержку запуска службы на Windows не предполагают. Проверяйте платформенные изменения в Linux/WSL или CI и явно указывайте ограничения локальной проверки.

- Для изменения поведения добавляйте целевые тесты в существующий соответствующий модуль. Используйте fake-клиенты, `httpx.MockTransport` и временную SQLite; реальные Telegram/LLM не требуются.
- После изменений Python запускайте полный unittest-набор; после изменения установщика также проверяйте Bash-синтаксис. Для правки только документации достаточно проверки содержимого и diff.
- В `pyproject.toml` задана конфигурация Ruff (`py312`, 100 символов), но Ruff не входит в зависимости и не запускается в CI. Не представляйте его как существующую обязательную проверку и не меняйте весь код ради форматирования.
- Прямую зависимость `httpx` согласовывайте между `pyproject.toml` и `requirements.in`. `requirements.txt` содержит скомпилированные закреплённые транзитивные версии; обновляйте его осознанно, через `uv pip compile requirements.in -o requirements.txt --python .venv/bin/python` в подготовленном окружении.
- `python -m tg_llm_bot --config <путь> --check-config` только проверяет конфигурацию и не обращается к API; нужны заполненные ключевые поля. Обычный запуск и `--remove-webhook` выполняют реальные запросы.

## Установка и эксплуатация

- Установщик поддерживает интерактивный режим, `--update` с сохранением существующей конфигурации и `--non-interactive` с окружением. Секреты не передаются аргументами команд; файл конфигурации заменяется атомарно.
- Пути на VPS: конфигурация `/etc/telegram-llm-bot/config.json`, данные `/var/lib/telegram-llm-bot/bot.sqlite3`, версии `/opt/telegram-llm-bot/releases/`, ссылка `/opt/telegram-llm-bot/current`.
- Служба работает от `telegram-llm-bot`. Сохраняйте права конфигурации `0640` (`root:telegram-llm-bot`), каталога данных `0700` и читаемость приложения служебным пользователем.
- Сохраняйте sandbox systemd и ограничения `CPUQuota=20%`, `Nice=10`, `MemoryHigh=192M`, `MemoryMax=256M`, если задача явно не требует их изменения. Учитывайте совместную работу VPS с VPN и другими службами.
- `Type=notify` зависит от `notify_ready()` после проверки Telegram-токена и отсутствия webhook. Сохраняйте готовность, корректное завершение и попытку восстановления прежнего release/config при неудачном запуске обновления.
- При существенном изменении установщика проверяйте `tests/deployment_smoke.sh` только в одноразовом Docker-контейнере Ubuntu 24.04 по команде из README. Скрипт изменяет системные каталоги, устанавливает пакеты и подменяет `systemctl`; на рабочем VPS его не запускают. Он имитирует запуск службы и не проверяет реальный systemd как PID 1 или внешние API.

Перед завершением просматривайте `git diff --check` и итоговый diff. В отчёте кратко укажите изменения, выполненные проверки и существенные непроверенные части. Не публикуйте и не развёртывайте изменения без соответствующей задачи пользователя.
